# 本地 AI 协作工作区设计

## 1. 目标

在本地建立一个由 Git 管理、可被不同 AI Agent 共同使用的工作区。任何新会话只需要读取少量固定入口文件，就能确定：

1. 当前有哪些工作事项；
2. 应该进入哪一个事项；
3. 已完成什么、正在做什么、下一步是什么；
4. 哪些动作可以自主执行，哪些必须先询问用户；
5. 本次任务需要补充加载哪些领域上下文。

工作区必须同时支持需求实现、问题排查、文档创作、检查复核等任务，不绑定单一 Agent 或单一模型。

## 2. 成功标准

- 根目录 `AGENT_GUIDE.md` 是唯一规范入口；其他 Agent 适配文件只转发，不复制规则。
- 每个工作事项在物理目录上隔离，拥有独立的 `STATUS.md`、`handoff.md`、过程记录、知识、草稿、工作区和归档。
- 新会话在不知道事项时先读总索引；知道事项时只读该事项的状态与交接文件。
- 固定核心行为始终加载；`coding`、`review`、`sync` 场景上下文按需加载。
- 每次有意义的工作结束、阻塞、切换模式或交接前，状态与交接文件同步更新。
- 所有关键状态最终提交到 Git；不使用会话记忆作为唯一事实来源。
- 仓库提供机械校验，阻止缺失状态文件、错误目录结构或未纳入索引的活动事项进入提交。
- 提供新建事项与生成上下文加载清单的命令行工具，减少不同 Agent 的执行差异。

## 3. 非目标

- 不自动调用或编排外部 Agent 服务。
- 不内置云端同步、账号、数据库或 Web 服务。
- 不代替用户决定高风险操作，例如发布、发送消息、部署、删除或改写历史。
- 不把所有历史内容一次性注入上下文；历史通过状态摘要、交接和按需检索恢复。

## 4. 核心结构

```text
AGENT_GUIDE.md                 唯一规范入口与会话启动协议
AGENTS.md / CLAUDE.md / ...    不同 Agent 的薄适配层
WORK_INDEX.md                  活动事项总览
context-router.md              场景识别与按需加载路由
core/                          始终加载的行为不变量
contexts/                      coding / review / sync 场景上下文
work/active/<item-id>/         正在工作的、物理隔离的事项
work/archive/<item-id>/        已结束事项
templates/work-item/           新事项模板
knowledge/                     已验证、可复用的跨事项知识
scripts/workspace.py           建项、上下文清单、结构校验
tests/                         CLI 与目录契约测试
.githooks/pre-commit           提交前结构校验
```

每个活动事项包含：

```text
work/active/<item-id>/
  STATUS.md                    当前事实：完成、进行中、待办、阻塞、验证
  handoff.md                   下一步、必读顺序、禁止重复、已知坑
  brief.md                     目标、验收标准、范围、约束、开放问题
  decisions.md                 有代价的决策记录
  journal/YYYY-MM-DD.md        追加式过程记录
  knowledge/                   本事项沉淀，验证后可提升到根 knowledge/
  drafts/                      尚未定稿的文档与中间稿
  artifacts/                   可交付结果与证据
  workspaces/<stream>/         隔离的操作工作区，例如需求实现与故障排查
  archive/                     本事项内部的历史版本与归档
```

### 4.1 状态职责

`STATUS.md` 回答“现在在哪里”，保持简洁并覆盖最新事实：

- 已完成；
- 正在做；
- 下一步；
- 阻塞与待确认；
- 最近验证；
- 当前边界与有效不变量。

`handoff.md` 回答“新 Agent 如何立即继续”：

- 唯一下一步；
- 必读顺序；
- 已完成、不要重复；
- 已知错误与不要踩的坑；
- 可直接运行的验证；
- 禁止或需确认的动作。

`journal/` 只追加，不覆盖历史。`STATUS.md` 和 `handoff.md` 是可被更新的当前视图，历史事实由 Git 和 journal 保留。

## 5. 渐进式加载协议

### 第 0 层：每次会话必读

- `AGENT_GUIDE.md`
- `core/invariants.md`

这一层只放行为边界、权限规则、恢复规则与完成标准，不承载具体任务状态。

### 第 1 层：事项恢复

- 不知道事项：读取 `WORK_INDEX.md`，选择或询问。
- 已知事项：读取该事项的 `STATUS.md` 与 `handoff.md`。
- 新事项：读取模板说明并创建事项，然后补齐 `brief.md`。

### 第 2 层：场景执行

由 `context-router.md` 判断并加载：

- `contexts/coding.md`：实现、修复、重构、测试驱动开发。
- `contexts/review.md`：审查、核验、回归检查、风险判断。
- `contexts/sync.md`：状态同步、交接、提交、归档、知识提升。

混合任务按“执行上下文加载 -> 检查上下文加载 -> 同步上下文加载”的顺序组合。模式切换、上下文压缩后、交接前后必须重新执行路由判断。

### 第 3 层：按引用读取

只读取 `handoff.md`、代码、文档或知识索引明确引用的文件。禁止无差别加载整个仓库或所有事项。

## 6. 自主权与询问规则

Agent 可以自主执行：

- 只读调查、检索和验证；
- 在已确认事项范围内、可逆、低风险的编辑；
- 创建草稿、过程记录和本地提交；
- 更新状态与交接文件；
- 运行不会破坏数据的测试和检查。

必须先询问用户：

- 目标、范围或验收标准存在会改变结果的歧义；
- 删除、覆盖用户内容、改写 Git 历史；
- 发布、部署、付费、发送外部消息或推送共享分支；
- 使用密钥、生产数据或扩大权限；
- 可能影响其他事项或工作区之外的文件；
- 多个事项都可能是目标，无法仅凭现有记录判断；
- 规范、用户指令和现有实现发生不可调和的冲突。

询问时只问一个决定性问题，并给出推荐默认值；不妨碍继续的低风险调查应先完成。

## 7. Git 协议

- 一个有意义的工作检查点对应一次提交。
- 提交信息使用 `item(<item-id>): <结果>`。
- 提交前必须运行 `python scripts/workspace.py validate`。
- 状态和交接必须与产生它们的工作处于同一提交，或紧随其后立即提交。
- 不默认推送远端。推送、合并共享分支、改写历史均需用户明确要求。
- 并发 Agent 先读取目标文件再写入；过程记录采用追加；共享的 `STATUS.md` 与 `handoff.md` 只在整合检查点更新。

## 8. 命令接口

```text
python scripts/workspace.py new-item <slug> --title <title> [--workspace <name> ...]
python scripts/workspace.py context <item-id> --mode auto|coding|review|sync
python scripts/workspace.py validate
```

- `new-item` 在 `work/active/` 下创建隔离目录、填充模板并登记 `WORK_INDEX.md`。
- `context` 输出当前任务必须读取、按模式读取和按引用读取的文件路径，不倾倒全部内容。
- `validate` 检查根文件、活动事项结构、必需标题、索引登记和重复 ID。

## 9. 文档连续性

新文档必须：

1. 先读目标事项的 `handoff.md` 和相关最新 journal；
2. 在文档头记录来源事项、前序文件和当前状态；
3. 新稿放入 `drafts/`，定稿后移入 `artifacts/`；
4. 沿用现有术语与格式，不另起不兼容的文档体系；
5. 在 `STATUS.md` 记录文档位置和下一步。

## 10. 行为不丢失机制

- `core/invariants.md` 是行为不变量，任何场景都不能跳过。
- 每个事项的 `brief.md` 保存用户原始要求、验收标准和有效约束。
- `STATUS.md` 的“当前边界与有效不变量”保存本次工作必须继续遵守的摘要。
- `handoff.md` 的“禁止重复”和“已知坑”防止新会话倒退或重复失败。
- 结束前必须对照 `brief.md`、当前边界和验证结果做一次行为回归检查。
- 任何模式切换、压缩恢复、交接或归档，都重新加载核心、状态、交接与路由相关上下文。

## 11. 并发与隔离

- 不同事项的目录是并发写入边界。
- 同一事项中，不同操作流放入不同 `workspaces/<stream>/`。
- 同一文件的并行编辑不做自动覆盖；发现外部改动时保留并整合。
- 跨事项操作必须先说明原因，并作为独立检查点提交。
- 根目录规范变更属于高影响变更，必须验证所有适配入口仍指向同一规范。

## 12. 验收方式

- 自动测试覆盖建项、上下文清单和结构校验。
- 使用临时目录创建示例事项，验证生成结构与索引。
- 验证所有适配文件都只指向 `AGENT_GUIDE.md`。
- 安装 Git hook 后，一次合法提交通过，一次故意缺失 `STATUS.md` 的提交被拒绝。
- 在仓库中创建一个真实可用的示例事项，证明新会话可按加载协议恢复，随后归档到演示位置。
