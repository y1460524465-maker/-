# Coding Context

仅在实现、修复、重构、测试或构建类任务中按需加载。

## 开始前

1. 已读取核心、事项 `STATUS.md`、`handoff.md`、`brief.md`。
2. 已确认目标事项与允许写入的工作区。
3. 已知本次验收标准和验证命令。
4. 已检查 Git 中是否有他人未提交的改动。

如果 handoff 的执行入口已经失效，先修正记录并说明，不盲目沿用过时路径。

## 执行规则

- 改动尽量局限在当前事项的 `workspaces/<stream>/` 或明确关联的代码位置。
- 先理解现有结构，再按最小可行改动实现。
- 代码行为变更使用测试先行：先写失败测试，确认失败原因，再写最小实现，最后运行完整相关测试。
- 文档、配置和结构工作也要有可重复的验证方式，例如链接检查、结构检查、命令输出或人工核验记录。
- 不顺便重写无关代码，不把样式、依赖和架构清理混入同一交付。
- 保留用户已有改动；冲突时整合，不覆盖。
- 发现范围变化、验收标准歧义或破坏性动作时按 `01-agent-layer/AGENT_GUIDE.md` 询问。

## 行为防丢失

每次实现后检查：

- `brief.md` 的每一条验收标准是否仍被满足；
- `STATUS.md` 的“当前边界与有效不变量”是否有被本次改动违反；
- handoff 中的“已知坑与禁止动作”是否被绕过；
- 新实现是否让已有工作流出现回归。

## 过程记录

以下节点追加 journal：

- 确认关键入口或完成一块可验证实现；
- 测试从失败转为通过；
- 发现重要依赖、限制或错误假设；
- 需要改变原计划；
- 准备交给 review 或 sync。

## 结束前

1. 运行与改动匹配的测试/检查，并读取完整结果。
2. 记录实际命令与结果。
3. 更新 `STATUS.md` 的已完成、正在做、最近验证。
4. 把下一步、未完成风险和验证入口写进 `handoff.md`。
5. 切换到 `review` 或 `sync`；不要只凭“代码看起来对”宣布完成。
